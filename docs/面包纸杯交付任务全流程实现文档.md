# 面包纸杯交付任务全流程实现文档

版本 1.1　编制及采集功能更新日期 2026 年 10 月 15 日

适用系统：xArm7 单臂、Quest VR 遥操、全局与腕部 RGB 相机、π₀.₅ 策略、STEAM 与 CFG 后训练。

本文用于指导数据采集、数据治理、模型训练、在线执行和连续服务功能的开发。核心方案是一杯一次任务：从准备状态出发，取一片橙色面包放进纸杯，再将同一个纸杯交给顾客；交接成功后结束任务 episode，由独立控制器撤离和复位。主策略无需同时学习返回初始姿态。

本文中的“已有”指当前项目文件中存在对应实现，不代表完成现场验收。“新增”指拟实现接口、字段或流程。参数建议用于起步实验；机械臂工作空间、运动限值、交接区域与人机接触条件必须通过现场标定和验证确定。本次交付为实现设计，不代表训练、自动接杯检测或自动复位功能已经上线。

## 0 本次已实现的采集方案（用户确认版）

本节是对后续设计基线中采集部分的实施修订，优先于第 2、5、6、8、17、18 节涉及连续录制与片段导出的建议。
用户明确保留扳机采集：按住且有效跟随才记录，松开不写入图像和机器人样本；再次按住接到同一条任务。
交接后继续按住扳机观察几秒，人工确认顾客接稳、夹爪释放后松开并结束。没有自动接杯检测、自动成功倒计时或自动复位。

### 0.1 操作流程

1. 在机械臂停稳、遥操禁用且没有未处理采集时，使用“记录 / 更新初始位姿”。已有目标无需重复记录。
2. 准备相机，填写任务描述，启用遥操并确认追踪有效，开启本条。
3. 按住扳机录制，松开暂停，再按继续；暂停期间预览继续，不生成虚假动作或图像。
4. 交接完成后按住扳机观察几秒，再松开等停稳，点击“结束本条 / 判定并保存”。
5. 采集器先冻结本条，再弹窗要求人工选择“成功”或“失败”，并单独选择是否保留。
   没有默认成功；取消弹窗保持冻结，稍后可重新打开。判定期间再按扳机也不会追加录制。
6. 保留失败轨迹是有效选择；丢弃标记为 discarded，不导出，原始文件仍保留以便追溯。
   数据质量不完整的记录不能因人工选择成功就成为完整可训练数据。
7. 保存或丢弃后，在采集页“禁用遥操（复位前）”→“检查复位路径”→“返回初始位姿”，沿用原人工确认流程。

### 0.2 同一任务只保存、导出一个 episode

原始档案继续使用兼容的 `xarm7.raw.v1`，添加人工审核元数据，无需改写既有文件。
每条任务保持一个 `raw.sqlite3`；导出为一个 episode Parquet 和每相机一个 MP4，不再按扳机区间另建 episode。
导出的 `timestamp` 和 `frame_index` 是压缩暂停后的播放时钟；实际采样时刻仍在 `source.monotonic_s` 和 alignment 中。
`capture.segment_index`、`next.discontinuity` 与 export_manifest 的 `training_windows` 保留间断，不能将其解释为无中断物理轨迹。
导出仍校验每个按压区间内的丢包、图像时间偏差和重复帧；短到无法对齐的区间拒绝导出，不静默删去。

训练动作块与 STEAM 时间帧对不能跨暂停边界。标准 LeRobot loader 不会自动识别这些项目扩展字段；
`recording_training.py` 提供完整数据集上的窗口筛选，可用 `restrict_training_windows(ds, export_root, horizon=30)`
包装配置好时间偏移的完整 LeRobotDataset。OpenPI 实际训练 loader 仍需接入筛选，不能只注册模型配置。

### 0.3 LeRobot v2.1 人工结果标注

官方 v0.3.3 的评估数据采用 `next.done`、`next.success`、`next.reward`；这些不属于所有数据集强制自带的默认字段，
需要在 `meta/info.json` 的 features 声明。本项目沿用前两个 bool 字段，不臆造 reward。
依据：[官方评估源码](https://github.com/huggingface/lerobot/blob/v0.3.3/src/lerobot/scripts/eval.py)、
[v2.1 数据默认字段](https://github.com/huggingface/lerobot/blob/v0.3.3/src/lerobot/datasets/utils.py)。

| 字段 | 非末帧 | 成功末帧 | 失败末帧 | 旧未标注末帧 |
| --- | --- | --- | --- | --- |
| next.done | false | true | true | true |
| next.success | false | true | false | false |
| annotation.success_valid（项目扩展） | false | true | true | false |

这里的末帧是最后一段的最后有效记录行，不是每次松扳机前的一行；没有额外伪造终止后动作。
人工事后标签表示整条任务的最终结果，不表示自动识别了成功发生时刻，也不把此前各帧都标成成功。
原始 `episode.json` 中的 `review` 及 SQLite `operator_review` 事件保留来源、审核时间、结果和保留选择。
导出 `meta/episode_annotations.jsonl` 及 `meta/episodes.jsonl` 保存整条结果与原始 ID，末帧字段直接进入 Parquet。
默认仅导出完整保留的成功轨迹；可勾选导出失败。旧未标注数据只能通过 `--include-unsuccessful` 显式纳入，且有效性掩码为 false。

### 0.4 初始位姿的持久化和复用

复用 `quest_joint_recovery.py`，目标长期保存在项目根目录的 `relative_home.json`，通过临时文件替换保存，
重新启动 GUI/控制器后读取，并检查机器人序列号、TCP/world 坐标配置。记录新的初始位姿会覆盖原目标，不会移动机械臂。
返回目标仍是 TCP Pose，不保证七关节构型完全一致。采集页提供记录、检查和返回按钮；本条尚未保存或丢弃时，
两页的初始位姿/复位入口均禁止执行。沿用低速路径核验与人工净空确认，不自动在成功后返回，也不改变现有现场目标。

以下章节保留完整系统的后续设计，`task_continuous`、raw.v2、自动交接和策略训练不属于本次上线范围。

## 1 任务定义与版本边界

### 1.1 单次任务目标

任务指令统一为：“从白色托盘夹取一片橙色面包，放入一个空纸杯，再夹取刚才装有面包的同一个纸杯，递给前方顾客，并在顾客接稳后松开夹爪。”每次只处理一片面包和一个杯子。多片装杯、更换顾客位置、追踪移动顾客等属于后续任务版本，不能静默混入首版数据。

建议新任务标识为 `bread_cup_handover_v1`，保留现有 `paper_cup_handover` 空杯任务。新任务指令、成功条件、交接模式和目标选择规则一经冻结，变更必须产生新 task_version。

初始条件包括：机械臂处于批准的准备姿态范围；夹爪为空且处于规定开度；至少有一片可夹取面包和一个可用空杯；双相机、机器人反馈和控制器时间戳有效；工作区与交接区满足运行条件。机械臂准备姿态可以有小幅受控变化，不要求各次记录完全相同。

### 1.2 成功与失败

业务成功必须同时满足：面包已放入目标杯；取起的是同一个杯子；顾客稳定持有该杯；夹爪已释放且杯子不再依赖机器人支撑。单凭手接近杯子、夹爪张开、物体离开画面或策略停止，均不能确认成功。

首次满足成功条件后，记录成功事件及释放后的观测，关闭本次任务控制权限，进入等待撤离状态。撤离许可单独判断，不由成功事件自动替代。

| 结果字段 | 含义 | 训练处理 |
| --- | --- | --- |
| success | 达到完整交付目标 | 可作为成功示范候选 |
| failure | 已确认任务失败，例如掉落、拿错杯 | 保留为 rollout 或失败分析 |
| truncated | 超时、人工中止、外部原因结束，结果未完整观察 | 不当作成功，也不自动视为语义失败 |
| unknown | 已结束但暂未标注结果 | 待复核 |

文件完整性另设 `recording_status`：recording、finalized、incomplete、discarded。完整保存的失败轨迹仍然是有效原始数据；损坏文件不能靠填写 success 修复。对掉落后重新完成的情况，保留事件序列，是否计为成功由 task_version 的规则决定，不能只看最终画面。

### 1.3 两种交接模式

| 模式 | 学习片段终点 | 等待与释放执行者 | 业务成功终点 |
| --- | --- | --- | --- |
| full_handover | 已释放且交接成功 | 策略提出动作，执行层检查释放许可 | 顾客接稳并脱离夹爪 |
| assisted_handover | 装杯后递到交接准备位 | 独立交接控制器负责保持、确认和释放 | 顾客接稳并脱离夹爪 |

默认研究目标使用 full_handover，符合“完整任务到交付成功”的定义。首轮真机验证可采用操作员确认接取许可和成功结果，明确记为人工辅助，不计入全自动成功率。如果长等待让进展评分不可靠，先上线 assisted_handover，并使用独立任务指令和导出配置；不能把准备位到达当作完整交付成功。

## 2 当前项目能力与改造范围

以下结论来自当前工作目录源码和 README。旧版 `xarm7-vr record` 的链路与当前相对遥操录制不同，实施以 `quest_pose_viewer.py` 及独立 recorder 为基础。

| 模块 | 当前实现 | 本方案所需改造 |
| --- | --- | --- |
| quest_pose_viewer.py | 遥操与采集界面、停止及人工恢复入口 | 增加任务阶段、完成原因、人工确认和模式显示 |
| quest_recorder.py | 双相机、遥测、独立录制进程 | 增加连续任务录制和 episode 生命周期 |
| recording_gate.py | 按扳机建立有效采集区间 | 分离录制许可与运动许可 |
| recording_data.py | xarm7.raw.v1、SQLite、时间对齐 | 增加 v2 schema、来源、事件和有效性掩码 |
| export_recording.py | LeRobot v2.1 与 RoboTwin 导出 | 增加完整任务视图、分组拆分、训练掩码 |
| openpi_xarm7.py | 8 维输入输出及配置工厂 | 在选定 OpenPI 和 RLinf 版本完成联调 |
| 初始 Pose 恢复逻辑 | 人工确认后低速关节路径恢复 TCP | 增加独立撤离阶段与运行状态机 |
| 新任务配置 | 现有配置仅为空杯交接 | 新增面包装杯交付配置，不覆盖旧任务 |

当前最重要的限制是 `capture_mode=trigger`：松开扳机后不保存图像和关节样本，导出时每个有效按压区间成为独立片段。这适合保存连续控制片段，但不等价于完整业务 episode。等待接杯、松扳机期间的夹爪操作和最终成功证据可能缺失。不能通过拼接这些片段伪造完整专家轨迹。

当前恢复的是 TCP 位姿，不保证回到历史七关节角组合；现有检查不包含完整环境碰撞或自碰撞检测。因此，现有“检查通过”不足以直接启用无人值守自动复位。

现有 `tasks/paper_cup_handover.json` 标记为空杯、固定交接点、不追踪人、交接时不释放，且工作空间和多个目标位姿尚为空。新流程不得直接沿用其成功定义或把示例坐标视为已批准现场参数。

## 3 总体架构与控制权

系统分为传感记录、任务监督、动作执行、离线学习四个部分。recording 服务只记录；所有机器人写操作经过同一执行器。VR、策略、交接保持和复位控制器通过控制权仲裁器取得独占权限。

```text
Quest 输入 ──→ VR 控制提案 ───────┐
策略服务 ────→ 动作块提案 ────────┤
交接控制器 ──→ 保持或释放提案 ────┤
复位控制器 ──→ 撤离与返回提案 ────┤
                               ↓
任务监督器 → 控制权仲裁 → 执行检查 → xArm7
                               ↓
双相机与机器人反馈 → 连续记录 → 数据审查与导出
                               ↓
专家 SFT → 策略 rollout → STEAM 评分 → CFG 后训练
```

新增 `owner` 取值为 NONE、VR、POLICY、HANDOVER、RESET；同一时刻最多一个 owner。每次切换递增 `control_epoch`，清空旧动作队列，作废进行中的推理请求，并等待机器人停稳或完成经批准的平滑交接。晚到响应只有在 episode_id、request_id、control_epoch 和模型版本均匹配时才可接收。

监督器管理业务阶段，执行器检查动作是否合法；STEAM 只参与离线评分，不拥有机器人控制权，也不承担实时完成检测。所有运行日志记录 proposed_action、accepted_command、执行反馈和拒绝原因，防止把策略提案误认为真实动作。

## 4 状态机与事件顺序

### 4.1 业务状态机

| 状态 | 进入条件 | 正常退出条件 |
| --- | --- | --- |
| IDLE | 没有正在执行的任务 | 操作员或调度器请求准备 |
| PRECHECK | 检查机器人、传感器和场景 | 准备条件全部满足 |
| READY | 准备姿态稳定、材料充足 | 显式启动新任务 |
| EXECUTING | 已创建 episode 并取得控制权 | 到达交接区或出现异常 |
| WAIT_RECEIVE | 杯子在批准的交接区域内稳定保持 | 接取许可已确认 |
| RELEASING | 接取许可有效，允许释放 | 获得释放后的新观测 |
| VERIFY_SUCCESS | 释放完成，结果尚待确认 | 成功、失败或超时 |
| SUCCESS_HOLD | 成功已锁存，策略权限已撤销 | 人手撤离且复位路径可用 |
| RETRACTING | 获得 RESET 权限 | 退出交接区域 |
| RESETTING | 已到撤离中间点 | 准备姿态与速度容差满足 |
| FAULT_HOLD | 任意状态遇到控制或感知故障 | 人工处理并重新执行检查 |

EXECUTING 内部记录 pick_bread、place_bread、grasp_loaded_cup、present_cup 等阶段事件。第一版阶段事件可由采集操作员标注；在线不默认获得这些真值。若阶段用于模型输入或切换策略，必须实现相同语义的在线估计器。

### 4.2 完成处理的原子顺序

收到成功候选后先继续获得足够的释放后证据，再由监督器确认成功。确认操作应一次性锁存结果、撤销 POLICY 权限、递增 control_epoch、清空动作块并进入保持状态。随后提交终止观测和事件、刷新原始文件、将任务 episode 标记 finalized。复位记录使用同一 cycle_id 下的独立 reset_id。

原始日志写入失败时仍应优先撤销策略权限并保持；同时将本条标为 incomplete。文件保存成功不能成为停止策略的前置条件。成功事件可重复到达，但不得重复释放夹爪或重复触发复位。

### 4.3 异常与接管

相机过期、机器人反馈过期、推理超时、动作不合法、设备故障和人工停止均先中止当前动作块。手工接管必须清除旧策略输出，重新锚定 VR 相对位姿，再允许操作。保留接管前失败过程及接管后的恢复动作，并按控制权切换建立学习边界。

超时不得自动松开仍在抓持的杯子，也不得把持杯手臂直接送回 home。应保持或按经过验证的异常处置流程放回安全位置。故障复位和正常交付后的复位必须分开。

## 5 连续采集与操作规程

### 5.1 新录制模式

新增 `capture_mode=task_continuous`。显式开始任务后持续记录图像、实测状态、已接受命令、运动状态和事件，直到任务结束；松开扳机只影响运动控制，不停止记录。预览可以始终开启，正式文件仅在任务或独立复位记录期间写入。

建议保留约 0.5 秒起始缓冲和约 0.5 秒终止观测作为调试初值。缓冲不自动进入策略或 critic 训练；导出依据任务起点、动作有效性和终止证据确定范围。终止观测是一条 observation，不要求伪造其后的 action。

松扳机后的制动过渡也记录，但标记为 `control_transition`。稳定保持阶段只有在执行层明确记录其保持命令和语义时才允许训练 action。缺少命令不能简单填成“当前关节位置”并假称实际下发。若控制接口是 latched target，必须记录目标持续生效区间和有效截止条件。

当前 training_vectors 还要求有效 Quest 来源及 motion 模式。新增策略、交接和复位记录后，应按 owner 检查相应来源，不能因 POLICY 模式没有 Quest 追踪就拒绝全部数据，也不能取消所有来源检查。VR 检查追踪与相对基准，POLICY 检查观测和推理请求，HANDOVER 与 RESET 检查其控制许可；主任务导出仍明确排除 RESET。

### 5.2 每批开始前

固定并拍摄相机安装位置、镜头设置、托盘位置、纸杯区域、交接区域及机械臂准备姿态。记录工具、负载、TCP/world 偏置、机器人序列号、固件和代码版本。校验腕部图像旋转、RGB 通道顺序、夹爪开度含义和左右方向；记录相机配置实际读回值。

全局相机应能辨认托盘、杯子和交接区；腕部相机应尽量看见夹爪、杯口和面包落入杯子的过程。若两路都看不到杯内状态，应调整视角或增加观测，不用“按时间猜阶段”代替可观察性。

使用短记录检查图像和关节同步、杯子释放前后是否保存、停止是否生效。相机主机时间不是曝光时间，应通过可见动作或闪光事件估计实际延迟，并保存同步校准版本。

### 5.3 单条专家示范

1. 复位并完成场景检查，为本条记录 batch_id、scene_id、操作者、物料数量和任务版本。
2. 显式开始新 episode，确认首帧、双相机和机器人状态已进入文件。
3. 取一片面包，放入选定空杯；保持真实、连续动作，不为避免视觉相似故意绕路。
4. 抓起同一杯子，递至交接区。顾客未接稳时保持抓持，不以固定等待秒数决定释放。
5. 顾客接取许可确认后释放；保存释放后的证据，确认成功或记录失败原因。
6. 结束任务记录，撤销任务控制权；确认撤离条件后启动独立复位记录。
7. 检查最终视频、关键事件和结果标签。材料减少属于下一条真实初始场景，不自动还原满桌物料。

采集失败不必立即删除；标注错误类型，必要时开启独立的纠正片段。用于训练 critic 的高质量专家子集应经过复核，成功结果本身不能证明中间没有长停顿、错误和往返纠正。

### 5.4 多目标选择

首版可在允许区域内任取一片面包与一个空杯，但必须抓回刚才装入面包的杯子。记录 target_cup_id 或其初始区域仅用于溯源；如果策略不接收目标 ID，不能依靠隐藏 ID 声称解决了多杯选择。

同一观测允许多个正确选择时，应覆盖这些合理选择，避免把“没有选专家选的杯子”一律视为失败。若用户指定杯子位置，语言指令和目标条件应明确；与任意空杯任务分开定义。

| 层级 | 关键字段 | 语义 |

| dataset | schema_version、task_version、device_profile | 固定数据契约 |
| episode | episode_id、cycle_id、session_id、scene_id | 溯源和防泄漏分组 |
| episode | outcome、termination_reason、recording_status | 区分业务结果与文件完整性 |

## 7 状态与动作契约

### 7.1 默认动作空间

沿用当前适配器的 8 维定义：前 7 维为关节角 rad，第 8 维为夹爪张开比例。state 来自实测，action 来自执行层已接受的目标。当前比例按开度毫米数除以 84 计算，0 表示闭合、1 表示张开；更换夹爪或有效行程后必须更新标定和模型数据版本。

模型保存绝对关节目标。OpenPI 输入变换将动作块内每个关节目标减去该块观测时刻的关节状态；输出通过配对变换恢复绝对值，夹爪保持绝对比例。不是对相邻未来动作逐项差分，也不是运行时对 delta 持续累加。

只执行一次 delta 变换。默认 `joint` 导出可以配合现有 `DeltaActions`；`joint_delta` 导出不得再次进入同一默认变换。模型内部 32 维填充不改变硬件只有 8 个输出量的事实。

### 7.2 时间与因果对齐

当前导出按主机时间选择最近机器人样本和图像，适合初始对齐，但尚未证明严格的 observation→action 因果关系。正式版本需建立观测快照时间 t_ref、各传感器实际采样或接收时间、命令发送及接受时间的对应关系。

输入采用在 t_ref 时已可用的观测，action 表示此后相应执行区间内的已接受目标；不得把执行该动作后才出现的图像混入它的输入。对于高频持续伺服目标，必须明确采样的是区间开始生效目标、区间内新目标还是重采样目标，并用回放验证确定唯一规则。

原始控制约 100 Hz、训练 30 Hz、模型输出 30 步属于三个不同频率概念。30 Hz 下 30 步约一秒；换成 20 Hz 后相同 horizon 覆盖约 1.5 秒，需要同步修改配置、评分窗口和部署节拍。

### 7.3 终点和掩码

记录最后一次有效动作及其后状态。末尾动作块不足 horizon 时，使用固定长度 padding 配合真实有效长度掩码，禁止把 padding 计入监督损失。若选定训练器不支持掩码，应先实现支持，或明确验证其原生末尾处理；不能默认它已经正确。

STEAM 的帧对必须在同一允许的连续区间内，未来观测不能越过任务终点。没有足够未来帧的最后一段不伪造优势；这些包含释放的关键动作仍可保留在 SFT 训练视图中，或者按明确的终端评分规则处理。

## 8 导出视图与旧数据迁移

保留统一原始库，生成互相独立且可追溯的训练视图。任何导出都保存源文件哈希、事件版本、切分版本、时间范围、转换配置和源帧索引。

| 视图 | 主要用途 | 准入规则 |
| --- | --- | --- |
| expert_sft | 初始策略训练 | 成功、语义正确、动作有效 |
| critic_expert | 时间顺序监督 | 高质量专家连续任务段，排除复位与严重歧义 |
| mixed_rollout | 优势标注与后训练 | 成功失败均保留，控制来源清楚 |
| correction | 人工纠正 | 保留接管前后关联，动作块不跨控制权切换 |
| evaluation | 固定独立评估 | 不参与统计量、阈值或模型选择训练 |
| reset_only | 复位诊断 | 不进入主任务策略或 critic |

连续任务可作为一个完整 episode，内部用 valid_span 和掩码限制帧对与动作窗口。若为了兼容读取器导出多个 clip，必须保留 parent_episode_id、业务结果与 clip 结果的区别。中途片段不自动标成“交付成功”，也不能不加说明地按短片段长度重新归一化成一个完整任务。

对旧 trigger 数据，只能导出实际存在的连续片段。缺失等待或最终释放观测的记录，不纳入完整交付 critic 专家集；有明确子任务语义的片段可作子技能 SFT。不能重复旧图像补齐未知过程，不能把多个按压区间压缩成一条无间断轨迹。

当前已有导出命令示例，路径需要替换，输出目录必须是新目录：

```bash
/home/a/download/lerobot/.venv/bin/python export_recording.py \
  /path/to/raw_dataset /path/to/new_v21_dataset \
  --format lerobot21 --fps 30 --action-space joint
```

已有 `--include-unsuccessful` 可纳入失败或未标注的完整文件，但不会纳入 incomplete/discarded。当前导出器尚不支持本文 v2 事件、掩码和完整任务模式；应新增版本分派和独立命令参数后再用于新数据，不能直接把版本字符串改为 v2。

## 9 数据质量与采集规模

### 9.1 自动质量检查

当前对齐检查包括相机偏差不超过 40 ms、机器人偏差不超过 25 ms、部分流的时间间断不超过 100 ms、相机图像索引复用不超过 10%、夹爪反馈年龄不超过 0.75 秒。这些是现有实现阈值，并非真实硬件曝光同步保证。尤其夹爪反馈约 2 Hz，不能单独承担精细接取检测。

新增检查包括：序号单调、时间戳单调、同一次进程启动的时钟域一致、RGB/尺寸/旋转一致、动作有限值与单位合法、owner 唯一、接受命令可追溯、终止观测存在、无跨复位动作块、相同父 episode 不跨数据集划分。

“重复帧”分开统计：相机序号重复是采样或复用问题；连续静止场景可以产生不同序号但相似内容；不同任务阶段的视觉混淆是模型问题。三者不能使用一个图像去重阈值处理。

### 9.2 人工复核

每条候选专家数据至少核验面包是否真正入杯、是否拿对杯子、是否由顾客接稳、释放证据是否清晰。优先检查末尾数秒、所有暂停、所有接管和抓取失败。保存剔除原因，便于判断问题来自遥操、传感器还是任务本身。

### 9.3 分阶段规模建议

先采 20 至 30 条试验数据打通全流程，再扩至约 100 至 200 条经复核专家示范作为起步预算。数量不构成收敛保证；根据成功率和失败类型的学习曲线决定是否追加。保留不同物料余量、杯子位置、可控光照、操作者和接取时延，避免只训练同一桌面布局。

数据划分建议按 session 或布置批次分组，再进行约 80/10/10 的训练、验证、测试划分。相同原始 episode 的所有片段、视频和纠正段必须在同一组；连续服务中高度相似的相邻轮次也优先留在同一组。小批试验可以用分组交叉验证，但最终测试集应锁定。

## 10 初始策略 SFT

### 10.1 训练前契约验收

固定 OpenPI、LeRobot、RLinf、CUDA、PyTorch/JAX 的版本或提交号。当前本地导出以 LeRobot v2.1 为默认；如训练环境要求 v3，应使用受支持转换流程并再次读取验证，不修改元数据版本冒充兼容。

现有 `openpi_xarm7.py` 映射全局相机至 cam_high、腕部至 cam_left_wrist，状态动作各 8 维；缺失右腕在模型内部用 false mask 标记。它提供配置工厂，但完整训练和真机执行仍需联调。OpenPI 自定义数据和模型配置机制以所固定 checkout 为准。[OpenPI 官方仓库](https://github.com/Physical-Intelligence/openpi)

用一小批真实导出数据完成读取、图像可视化、状态分布和动作反变换检查。重点测试同一个动作经“绝对→delta→归一化→反归一化→绝对”后恢复一致，夹爪方向不反转，填充维度不会下发给硬件。

### 10.2 训练步骤

1. 导出并冻结 expert_sft 的训练与验证划分，清点 task、相机与动作契约。
2. 将 XArm7 数据配置注册到实际 OpenPI checkout，登记配置名 pi05_xarm7。
3. 仅用训练子集计算归一化统计，绑定到数据版本与模型资产。
4. 从 pi05_base 初始化；先执行短训练检查数据和 loss，再进行完整 SFT。
5. 按验证表现保存候选 checkpoint；保留初始 SFT 作为不可变基线。
6. 进行无机器人动作的离线推理，再通过执行门禁进行受控真机评估。

现有工厂初值为 batch_size=8、action_horizon=30、30000 步；这些不是已验证的最优值或显存承诺。使用该 checkout 提供的 `scripts/compute_norm_stats.py --config-name pi05_xarm7` 计算统计，训练启动参数需与对应版本核对。训练日志至少包括数据版本、有效动作数量、学习率、梯度、验证损失和 checkpoint 路径。

### 10.3 采集 rollout 与纠正

SFT 达到可受控运行水平后，用冻结模型收集 rollout。保存成功、失败、停滞、人工接管和恢复过程；不为了增加失败数据主动制造碰撞。source_type 应区分自主策略和人工纠正，模型提出但被拒绝的动作另存，不能与已执行命令混为监督目标。

初始 SFT 优先使用干净示范，rollout 用于后续评分和改进。训练 loss 下降不代表真实交付成功率提高，模型选择必须包含独立任务评估。

## 11 STEAM critic 训练与诊断

### 11.1 机制与本任务适配

STEAM 利用专家帧对的有符号时间间隔学习相对进展，反向帧对提供负方向监督。若相同可见输入对应不同阶段和相反标签，就会产生歧义；隔离复位减少这种冲突，但不保证多杯选择、遮挡和等待问题消失。[STEAM 官方项目说明](https://rlinf.github.io/steam/)

critic_expert 只选经过审查的专家任务记录。第一版使用全局与腕部两路视觉、任务文字及已实现的输入契约；阶段 ID 和目标 ID 仅作诊断元数据。若引入阶段条件、状态或历史窗口，应另设实验版本，并确保评分时具有相同信息。

相机映射必须在 RLinf 实际读取器验证：本地字段 observation.images.cam_high 与 observation.images.cam_left_wrist 不等于其示例中的 face_view 等名称。选择显式别名适配或修改 camera_keys，并打印一次真实 batch 证明两路图像已读取。不能接受“缺失相机被零图填充但程序不报错”的假成功。

### 11.2 时间窗口与归一化

建议从 30 Hz 下约 0.5 至 1 秒的局部窗口开始比较，记录最大配对跨度 K 与评分前瞻 H 的物理时长。可以试验 K/H=16 或 32 帧，但两者含义和实际实现绑定关系需核对。分箱数量必须满足所选实现约束；更换帧率后按秒重新选择，不机械照搬帧数。

帧对不得跨过录制间断、复位、控制权切换或任务结束。对于完整 episode 中被排除的长等待段，应明确时间归一化分母的语义。不得删去等待帧后仍以新的连续帧号假装原始时间未变化；也不得用短 clip 长度替代完整任务长度而不重新定义任务。

### 11.3 必要等待的处理

先保留全部等待记录，并用 phase 标签检查评分。若等待阶段被系统性降权，优先采用 assisted_handover 缩小学习目标。另一方案是修改训练管线：纯等待帧对不参与时间进展损失，等待动作保留在独立 SFT 损失中；CFG 仅对可靠有效窗口使用优势标签。这需要实现 mask、采样器及混合损失，属于扩展方案，不能直接套用原版参数。

full_handover 必须保留释放前必要保持和释放动作，不能因优势分数较低全部删掉。剔除等待片段不等于允许提前释放；在线释放许可始终由独立条件约束。

### 11.4 训练入口与验证

RLinf 提供 ensemble critic 训练、优势计算和 π₀.₅ CFG 优化流程。官方示例中的配置名分别为 steam_value_model_sft、steam_compute_advantages_ensemble 和 cfg_rl_openpi。[RLinf STEAM 文档](https://rlinf.readthedocs.io/en/latest/rst_source/examples/embodied/steam.html)

建议复制官方配置为项目专用配置，先固定专家路径、相机映射、任务头、模型资产、配对规则与评估路径。配置中保留 ensemble_size=3 可作为起点，批大小和步数按硬件调节。训练集仅放 critic_expert；rollout 用于后续评分与独立诊断，不把所有 rollout 的正向时间顺序直接当作正确推进。

```bash
# 在已适配并固定版本的 RLinf 目录中执行
bash examples/offline_rl/advantage_labeling/steam/run_steam_sft.sh \
  steam_value_model_sft
```

除分类准确率外，必须输出按阶段的正反向判别、停滞与失败分数、各 ensemble 成员分歧以及成功末尾动作保留率。验证集合要包含外观相近的空爪伸手与撤离、抓错杯、空杯交付、遮挡、顾客迟接、成功释放等案例。若分数主要跟随机械臂位置而不是物体状态，应先改善观测或任务分解。

论文明确指出视觉可能漏掉关键状态差异，时间偏移也未必反映各阶段贡献差别。因此 critic 不能当作交接检测器或安全判定器。[STEAM 局限性](https://arxiv.org/html/2606.29834v2#S5)

## 12 优势标注与 CFG 后训练

### 12.1 优势产物

为 expert_sft 与 mixed_rollout 的可评分锚点计算优势，保存 dataset_id、episode_id、frame_index、源观测对、窗口长度、critic 版本、成员分数、聚合分数、标签规则及有效性。任何评分必须能够映射回原始录像。

按数据来源分别查看分布。官方流程支持阈值或分位数标签；项目应先比较保留比例和各阶段覆盖，再选择参数。不能以固定“保留前 30%”替代质量验证，否则可能系统性丢失等待、精细夹持和释放动作。分位数拟合只使用训练数据，不用测试集调阈值。

```bash
bash examples/offline_rl/advantage_labeling/steam/process/run_compute_advantages_ensemble.sh \
  steam_compute_advantages_ensemble
```

以上是官方入口示例，运行前仍需设置实际 checkpoint 和数据路径。训练与评分保持相机、预处理、状态开关和时间尺度一致；评分范围可包含未参加 critic 训练的混合质量数据。配置字段以固定版本为准。[优势计算配置](https://raw.githubusercontent.com/RLinf/RLinf/main/examples/offline_rl/config/steam_compute_advantages_ensemble.yaml)

### 12.2 模型衔接

从已验证 SFT 权重开始后训练，保持相同动作空间、归一化、相机和任务语义。现有本地工厂面向 OpenPI，RLinf CFG 示例使用其支持的模型包装；JAX checkpoint、PyTorch 权重和 CFG 包装不能假定可直接互换。需要选择统一训练后端，或执行受支持转换，并在固定输入上比对转换前后输出。

RLinf 示例默认 config_name 为 pi05_libero，应替换为真正注册的 XArm7 配置。model_path 指向适配后的 SFT 权重，不是继续使用默认占位路径。确认加载报告没有关键层丢失，随后进行单批次前向、反向和动作解码测试。[CFG 官方配置](https://raw.githubusercontent.com/RLinf/RLinf/main/examples/offline_rl/config/cfg_rl_openpi.yaml)

```bash
bash examples/offline_rl/policy_optimization/cfg_rl/run_cfg_rl.sh \
  cfg_rl_openpi
```

### 12.3 CFG 的使用与回退

CFG 是利用训练时条件与无条件分支进行动作生成引导，需要相应训练与推理包装支持。不能仅给普通 SFT 模型添加 guidance_scale 参数就宣称完成后训练。部署端必须加载 CFG 模型及正确分支语义，同时保留相同的图像和动作变换。

建议先以 guidance_scale=1 为参考，再小范围比较较高值，例如 1.5 与 2.0；这些是实验起点，不是可保证的优选参数。比较成功率、动作幅度、延迟、执行器拒绝率和必要等待行为。高引导强度不会自动修复错误标签。

至少保留 SFT 基线、加入纠正后的 SFT、STEAM 加 CFG 三组实验，尽量匹配数据和评估条件。若 CFG 未改善真实任务指标，则回退 SFT 并分析数据和评分，不因训练已完成而强行发布。

## 13 在线推理接口

### 13.1 输入输出契约

新增 policy_client 负责协议、序号、超时与模型版本；不得直接操作 SDK。推理请求包含 episode_id、control_epoch、request_id、obs_id、观测生成与发送时间、任务文字、8 维 state 和两路 RGB。返回包含对应标识、model_version、动作空间、训练节拍和 `[H,8]` 绝对目标块。

推理服务器负责应用与训练一致的模型变换，确保输出已恢复为物理单位。客户端必须知道返回的是绝对目标还是模型内部 delta；禁止双重反归一化或额外累加状态。

### 13.2 滚动执行

每次预测动作块只执行前 n 步后重新观测。以 30 Hz、H=30 为例，可从 n=3 至 6 步的短执行窗口试验，前提是实测端到端延迟和抖动能够满足更新期限。n 不应由示例固定，需根据推理耗时、机器人响应和交接阶段共同确定。

执行端将 30 Hz 目标转换为底层约 100 Hz 的受限平滑目标，并核验速度、加速度、关节限位、工具姿态和工作区。禁止把一秒的 30 步动作块在底层 100 Hz 直接压缩成 0.3 秒执行。插值方式和限速参数需要与采集期间的已接受动作含义对齐。

同步推理先实现“观测→推理→执行短片段→重观测”。若延迟导致频繁等待，再实现明确的异步调度与时间补偿；不能仅跳过前几帧假装解决延迟。任何丢弃过期动作的规则都要记录已跳过长度及当前观测时间。

### 13.3 执行检查

每个动作检查维度、有限值、关节单位、夹爪范围、相邻步幅、当前状态误差、工作空间及控制 epoch。轻微限幅应记录；明显越界、异常跳变或过期动作应拒绝并保持，不能长期静默夹紧错误输出继续运行。

发出成功事件、人工接管或停止时，不等待当前动作块自然结束。执行线程应在下一次控制检查立即作废旧队列，后续输出全部验证新的 control_epoch。实际制动时间和距离由现场测试获得，不以线程检查频率代替机械停止能力。

## 14 交接检测与完成信号

### 14.1 第一版人工确认

首版设置三个独立输入：receiver_ready 表示顾客已准备承接；success_confirmed 表示释放后杯子确实被接稳；retract_allowed 表示可撤离。操作员确认写入事件并显示确认来源，不能包装成模型自动理解。

在 full_handover 模式，策略提出张爪动作只有在交接区、持杯状态和 receiver_ready 有效时才允许执行；未获许可时由明确的保持命令维持抓持。所有被拦截提案和实际保持命令分开保存。策略如果在放面包阶段张爪，应依据该阶段的空间和任务条件执行，不能用一个全局“禁止张爪”规则阻止正常装杯。

### 14.2 自动检测升级

自动检测需要分别识别装有面包的目标杯、顾客的接取状态、夹爪与杯子的分离以及交接后的稳定性。可以结合全局与腕部视觉、物体跟踪和可用的力或触觉；当前系统没有可靠力觉时，不得把尚未测量的信号写成既有依据。

检测结果包含 confidence、evidence_obs_ids、时间有效期和状态。连续多帧确认用于减少瞬时误判，但帧数与持续时间应由检测器验证决定。杯子被手遮挡时返回 unknown 或保持，不能把消失当成功。夹爪开度变化只能证明夹爪运动，不能证明顾客拿稳。

完成检测与释放许可应单独评估假阳性、漏检和延迟。未通过自动检测验收时，系统保持人工确认模式。STEAM 分数不替代上述信号。

## 15 撤离与复位

正常复位仅在成功已锁存、夹爪不再持杯、撤离许可有效且路径检查通过时启动。流程为保持当前位置、退出交接区域、到达中间安全位、回到准备姿态、检查最终状态、释放 RESET 权限。各段由当前实测状态重新生成，不无条件回放采集时的历史路径。

准备姿态建议同时定义 TCP 容差、关节构型容差和速度容差。七自由度机械臂可能以不同肘部构型到达同一 TCP；如果训练数据要求固定关节初态，仅验证 TCP 不够。可选择固定批准关节构型，或采集并训练覆盖批准的构型范围。

当前项目人工恢复流程使用低速关节路径且不含完整碰撞检测。要实现自动循环，应增加经验证的撤离走廊、整臂扫掠范围检查和现场人手退出条件；未具备环境感知时，只能在受控场景与人工确认下使用固定验证路径。异常夹持、杯子未释放、机器人保护状态均进入异常流程，不自动清故障继续运动。

复位结束后检查材料余量、夹爪空载、观测新鲜度和准备姿态。缺面包、缺杯或上一杯身份不明确时请求人工补料或整理。只有允许连续模式且全部检查通过，才创建下一条 episode。

### 16.2 监督器伪代码

```python
def on_policy_reply(reply):
    if not matches_active_request(reply):
        return reject("stale_or_wrong_epoch")
    if owner != "POLICY" or task_is_terminal:
        return reject("policy_not_active")
    executor.replace_future_chunk(validate(reply.actions))

def on_confirmed_success(evidence):
    with supervisor_lock:
        if task_is_terminal:
            return
        latch_success(evidence)
        revoke_policy_and_increment_epoch()
        executor.cancel_and_hold()
        phase = "SUCCESS_HOLD"
    recorder.finalize_with_terminal_observation(evidence)

def maybe_reset():
    if success_latched and retract_allowed and path_verified:
        arbiter.acquire("RESET")
        reset_controller.start_from_measured_state()
```

实际实现还需处理线程间原子性、执行停止失败、日志写入失败、硬件状态变化和幂等事件。保持动作须使用已有控制器支持且经过验证的方式，不能将伪代码函数名直接映射成未经核验的 SDK 调用。

## 17 测试与验收

### 17.1 必须覆盖的自动测试

| 测试 | 输入或故障注入 | 通过条件 |
| --- | --- | --- |
| 连续录制 | 按住、松开、夹爪操作、等待 | 数据持续记录，运动权限独立 |
| 末尾保存 | 释放后立即结束 | 有最后有效动作及终止观测 |
| 文件恢复 | 录制中断或磁盘不足 | incomplete 可诊断，不标成功 |
| 数据边界 | 任务、接管、复位连续出现 | 动作块与帧对不跨禁止边界 |
| 动作变换 | 单位、delta、夹爪极值 | 往返误差合格，无双重变换 |
| 控制权 | VR、策略、复位竞争 | 同时仅一个有效 owner |
| 推理过期 | 超时、乱序、旧 epoch 返回 | 全部拒绝且无旧动作下发 |
| 成功锁存 | 重复成功事件 | 只终止一次，不重复释放 |
| 交接检测 | 遮挡、碰杯、未接稳、空杯 | 不误判业务成功 |
| 复位条件 | 人手未退、仍持杯、路径改变 | 不启动正常复位 |

先使用假 SDK 和录制回放测试状态机，再做仅观测的 shadow 推理，最后进行现场低速、受控范围测试。mock 通过不能替代真机的制动、抓持、交接与路径验收。

### 17.2 评估指标

分别报告面包夹取率、入杯率、正确杯抓取率、交接准备率、最终交付成功率、错误释放率、人工干预率、复位成功率和每杯总周期。最终交付成功率的分母是所有有效启动的任务，不仅是进入交接区的任务。

同时报告人工辅助和全自动两种结果，成功率附样本数与置信区间。超时和人工接管不能从分母静默删除；材料短缺等预检查失败另列。完整周期从任务启动至下一次准备就绪，包括等待与复位，避免只优化学习片段耗时。

推理性能记录观测年龄、推理时间、网络往返、动作队列年龄和停止响应的 p50/p95/p99。验收目标应由控制周期和实测制动确定；如果未满足时限，应降低执行节奏或调整架构，而不是放宽过期动作检查。

### 17.3 发布门槛

先确保契约与故障注入测试全部通过，再在锁定测试布局上对比 SFT 和 CFG。建议每个候选至少进行 30 至 50 次受控评估，作为初步工程判断；这不构成对稀有失败的统计保证。另做连续多轮服务，检查物料减少、等待变化和复位误差积累。

自动交接发布前，需单独证明接取许可与成功检测的误判水平满足项目要求。自动复位发布前，需通过有人手延迟撤离、不同末端姿态及路径受阻测试。未达标时继续使用明确标注的人工确认模式。
